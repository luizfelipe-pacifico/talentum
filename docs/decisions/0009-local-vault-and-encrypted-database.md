# ADR 0009 — Local vault, encrypted database and desktop sign-in

- Status: accepted
- Date: 2026-11-20

## Context

Until now anyone who could open the computer, or copy the SQLite file, could read every balance, statement and transaction: the local app had no login and the database was plaintext. Only own Pix identifiers were encrypted, with a device key stored next to the database ([ADR 0003](0003-local-device-key.md)), which protects a copied database but not a copied folder. The maintainer asked for a login in the downloaded app ("imagine someone gets access to the computer or phone"), encryption of everything, an authenticator app as a second factor, and account creation through Google. Talentum ships for Windows, Linux and macOS; Docker is used only for development.

## Decision

1. **Local vault.** On first run the person creates a local password (at least 12 characters, a blocklist of common passwords, a visible strength estimate; NIST SP 800-63B §3.1.1.2). A random 256-bit data-encryption key (DEK) encrypts the database. The DEK is wrapped with AES-256-GCM twice: under a key derived from the password with **scrypt (N = 2^17, r = 8, p = 1, 32-byte key, 16-byte salt per wrap; OWASP Password Storage Cheat Sheet)** and under a key derived the same way from a one-time **recovery code** (160 bits, Crockford Base32, shown once, confirmation required). The wrapped keys, the TOTP state, the auto-lock setting and the attempt counter live in `talentum-local.vault` next to the database, written atomically with mode `0600`. The DEK exists only in the memory of the local backend after unlock. Without the password or the recovery code the data cannot be read by anyone, including the project; there is no cloud escrow.
2. **Whole-database encryption with libSQL.** The database is opened through `@prisma/adapter-libsql` 6.19 with `@libsql/client` 0.8 and a `file:` URL with `encryptionKey` (the HKDF subkey `database` of the DEK). Dates use `timestampFormat: 'unixepoch-ms'`, the format the native Prisma engine already wrote, so migrated files keep their values. `src/server/db.ts` keeps exporting `db`, now a proxy that throws `VaultLockedError` while locked, so route code is unchanged.
3. **Own migration runner.** `prisma migrate deploy` cannot open an encrypted file. `src/server/vault/migrations.ts` applies `prisma/migrations/*/migration.sql` in name order through the encrypted connection at unlock (and setup), records each in `_prisma_migrations` in Prisma's format (SHA-256 checksum, start, finish, steps), refuses to continue after a failed migration and blocks destructive migrations without a verified backup (the gate that used to live in `scripts/migration-preflight.mjs`, now applied in development, Docker and the packaged app alike). New migrations are authored with `pnpm prisma:migrate`, which runs `prisma migrate dev` against a disposable plaintext scratch database.
4. **Legacy plaintext databases** are copied table by table into a new encrypted file at setup, verified (row count of every table and `PRAGMA integrity_check`), swapped into place, and the plaintext file and its `-wal`/`-shm`/`-journal` are overwritten with random bytes and deleted after the vault is written.
5. **Sessions enforced centrally.** Unlock issues a random opaque session token in an `HttpOnly`, `SameSite=Strict`, `Path=/` cookie named per port (`Secure` only over HTTPS; the local app is loopback HTTP). Action codes, which every route already consumes, are issued only to a live session and bound to it; a code issued before a lock is refused. Only `GET /api/vault/status`, `POST /api/vault/setup`, `/unlock` and `/recover` work without a session. Idle auto-lock defaults to 10 minutes (1–60, set in Settings > Security), measured from real user input reported by the interface; "Bloquear agora" locks immediately; in the desktop app system suspend and screen lock (`powerMonitor`) lock too. Failed attempts get five free tries, then 30 s doubling up to 1 hour, persisted in the vault file; the error never says which factor failed.
6. **TOTP (RFC 6238)** is optional: SHA-1, 6 digits, 30 s, ±1 step, a used step is refused, ten single-use backup codes stored as HMACs. The QR is rendered locally. The TOTP secret is encrypted under the DEK, so it is an **enforced gate in the backend**, not extra cryptographic strength: someone who copies the files attacks the password and scrypt offline, never the TOTP.
7. **"Entrar com Google" on the desktop** creates or links the cloud account (downloads, updates, community) through the system browser following RFC 8252: PKCE S256, `state`, a one-shot loopback listener on `http://127.0.0.1:<random port>/callback`, a fresh public action code (`POST /api/public/action-codes`) on every request, and the refresh token stored only through Electron `safeStorage` (Keychain on macOS, DPAPI on Windows, libsecret/KWallet on Linux; not persisted with the `basic_text` backend). It never unlocks the local vault. The endpoint contract is in [ARCHITECTURE.md §4.7](../ARCHITECTURE.md#47-desktop-authentication).

## Alternatives

- **SQLCipher / SQLite3MultipleCiphers through `better-sqlite3`:** proven encryption, but `better-sqlite3` is not N-API, so it must be rebuilt for each Electron ABI and platform (Windows, Linux, macOS arm64 and x64), and Prisma 6 needs an alias override to swap the package. libSQL ships N-API prebuilt binaries for all three systems and an official Prisma adapter.
- **Argon2id:** preferred by OWASP, but needs a native dependency (`argon2`) with the same per-platform build cost; scrypt is in `node:crypto`, memory-hard and within OWASP's recommended parameters. Revisit when Node ships Argon2 natively.
- **Encrypting only sensitive columns:** leaves descriptions, amounts and the schema readable and every new column at risk of being forgotten.
- **OS keychain holding the DEK (no password):** convenient, but anyone logged in as the user opens the data, which is the threat the maintainer named.
- **TOTP secret outside the DEK (for example in the keychain):** would let the second factor be checked before decrypting, but adds platform code and still does not stop an offline attack on a copied database file.
- **Docker as an end-user distribution:** rejected; installers never require Docker ([ADR 0004](0004-electron-packaging.md)).

## Consequences

- Forgetting both the password and the recovery code loses the data, by design. The interface says so before the vault is created.
- `prisma migrate deploy`, `prisma studio` and any plaintext SQLite tool no longer open the database; the migration runner and the app are the only path.
- `scripts/migration-preflight.mjs` and `pnpm prisma:preflight` are removed. Their responsibilities moved to the open path `src/server/backup/startup.ts`, run at setup and every unlock before the runner: apply the scheduled restore, create the encrypted `pre_migration` restore point (which satisfies the destructive gate), then migrate. Restore points and encrypted backups stay encrypted at rest ([ADR 0007, amendment](0007-local-encrypted-backup.md#amendment-encrypted-database-adr-0009)).
- The DEK is zeroed on lock, but the hex key string handed to libSQL is an immutable JavaScript string and stays in the heap until garbage collected; memory forensics on a running, unlocked process is out of scope.
- Values above 2^53 cents in magnitude are not supported through the adapter (Prisma 6.19 sends large negative `BigInt` parameters incorrectly); the importer's ceiling (R$ 9.999.999.999.999,99) keeps every value well below it.
- The device key file of [ADR 0003](0003-local-device-key.md) still exists; it now sits next to an encrypted database. Wrapping it under the DEK is **Planned**.
- Overwriting the old plaintext file is best effort on SSDs, copy-on-write file systems and synced folders; full-disk encryption (BitLocker, FileVault, LUKS) remains the recommendation.
- No packaged build has yet confirmed that the libSQL native binary is traced into `.next/standalone` for each platform (**Open**, packaged smoke test).
